# 技能盘点

## 适用场景

用户想搞清楚「本机到底有哪些技能、哪些真的在用、哪些是冗余或放错位置了」时触发。

## 第一步：先确定「谁在扫描什么」，不要靠猜

**唯一可信的判据是目标工具自己的技能清单缓存**，不是目录里有什么文件，也不是配置文件里写了什么路径。

| 工具 | 判据文件 | 关键字段 |
|---|---|---|
| WorkBuddy AI | `~/.workbuddy-ai/.skill-list-cache.json` | `watch.dirs`（扫描目录）、`results`（已注册技能） |
| 旧版 WorkBuddy | `~/.workbuddy/.skill-list-cache.json` | 同上 |
| Claude Code | `~/.claude/skills/` | 无缓存文件，直接看目录 |
| Codex | `~/.codex/skills/` | 同上 |

用脚本读 JSON，不要肉眼扫：

```bash
python -c "import json;d=json.load(open('$HOME/.workbuddy-ai/.skill-list-cache.json',encoding='utf-8'));[print(x) for x in d['watch']['dirs']]"
```

**陷阱**：`settings.json` 里出现某个 `skills/` 路径，可能只是**文件读写权限预设**，不等于技能扫描路径。判定一律以 `watch.dirs` 为准。同理，旧版目录里的技能在新版工具中**完全不加载**——两个版本的配置目录（`.workbuddy` 与 `.workbuddy-ai`）互不相通。

## 第二步：逐项确认引用状态

对每个候选技能目录，按顺序查：

1. **是否落在 `watch.dirs` 覆盖范围内** → 决定会不会被加载
2. **是不是软链 / junction** → `ls -la` 看箭头，`readlink` 看真实目标
3. **链接目标是否存在** → 断链的技能不会显示
4. **目录内是否有 `SKILL.md`** → 没有就不会被注册成技能

统计时顺手分类：软链数 / 实体目录数 / 无顶层 `SKILL.md` 的仓库根 / 含多个 `SKILL.md` 的嵌套包。

## 第三步：识别四类问题

| 类型 | 判据 | 处置 |
|---|---|---|
| **位置不规范** | 有效技能但不在任何 `watch.dirs` 内 | 迁到正确目录，或建链接（推荐，不产生副本） |
| **重复** | 同一技能存在多份（嵌套仓库 + 顶层展开副本 + 拷贝） | 保留最浅路径 / 权威副本，其余删 |
| **功能重叠** | 两个技能描述高度相似（如 `playwright` 与 `playwright-skill`） | 保留维护更活跃的那个 |
| **废弃** | 无任何引用、无 git 跟踪、内容是旧快照 | 删除；有历史价值的先归档 |

**去重铁律**：

- 同名技能保留**最浅路径**（顶层优先）
- 唯一技能绝不删
- 判定「内容一致」前**先校验两侧路径都存在** —— `diff` 对不存在的路径会输出 0 行，会被误判成「完全一致 = 冗余」

## 第四步：出报告

按项目既有格式落盘 `<项目>/skills-audit-YYYY-MM-DD.md`，至少包含：

1. 一句话结论
2. 环境事实（实测，注明判据来源）
3. 逐项引用状态表
4. 重复 / 废弃 / 重叠清单
5. 已执行的变更（附校验方式）
6. 未执行项与原因

## 删除前的硬性检查

1. 全盘 `grep` 该目录名，确认无外部引用
2. 检查各工具 skills 目录有无指向它的软链
3. 确认无 git 跟踪
4. **先备份再删**；若用户选择直接删除，明确告知不可逆

## 边界

- 不修改技能内容本身（那是 `skill-creator` 的职责）
- 不删除有 git 跟踪的技能仓库（那属于版本管理）
- 涉及用户个人目录（Desktop / Downloads / Documents）时，**先出报告，等用户逐项确认再动手**
