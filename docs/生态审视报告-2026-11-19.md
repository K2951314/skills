## 1. 第一性原理框架

你的业务价值环是一条链：

```
厂商样本 PDF（知识源头）
  → 可信结构化数据（smart-selection 真源层）
  → 销售决策（报价 / 替代 / 库存 / 配刀 / 失效诊断）
  → 客户交付物（报价单、小程序答案、客户门户）
```

AI 智能体是这条链上的劳动力放大器。skill / agent / 工作流 / MCP 不是四种技术，而是**同一种东西（可复用的判断 + 可执行的能力）的四种包装形态**，选择判据只有四条：

1. **频率**：这件事一周做几次？（每天多次 → 必须包装；一年一次 → 写文档就够）
2. **判断密度**：里面有多少「踩过坑才知道」的隐性判断？（越高越值得沉淀成 skill 的铁律/闸门，而不是裸脚本）
3. **漂移风险**：换个机器/换个会话/换个客户端，它还能跑吗？（硬编码路径、写死模型名、只在一端可用，都是漂移）
4. **已有覆盖**：项目里是否已有机制？（有 → 包装或接线；没有 → 才考虑新建）

用这四条量下来，结论很清晰：**你的瓶颈不是缺框架**（ZK-AI 的网关/任务台/事件中台/委派层已经覆盖了 agent 与工作流的底座，且「总控大脑」文档已把剩余缺口排成 R2–R6 路线），**而是两类缺口**：

- **包装缺口**：大量已验证的业务能力只有 GUI/网页入口，没有 agent 可调用的形态；已包装的 3 个业务 skill 又带着旧机器死路径。
- **闭环缺口**：监测（三菱可用性、数据新鲜度、备份可恢复性）与反馈（未收录查询→补数据）已经建好了传感器，但没有点火器定期去读。

## 3. P0：实测发现的失效与漂移（先修这些，再谈沉淀）

### 3.1 三个新业务 skill 在本机全部失效（死路径）

实测证据：

- `E:\Ingulf` 在本机**不存在**（`Test-Path` = False）；真实项目在 `D:\zhangkun\智能询价` 与 `D:\zhangkun\smart-selection`（均存在，`quotation.db`、`web/substitute.py`、`web/_vendor/*.pycbin`、`paths.local.toml` 齐全）。
- `quotation-helper/scripts/quote.py` 第 19 行：`BACKEND_ROOT = r"E:/Ingulf/智能询价"`。
- `mitsubishi-inventory/scripts/stock.py` 第 16 行：同上。
- `tool-selection/SKILL.md`：命令写死 `E:/Ingulf/smart-selection/web/substitute.py`，修复指引还指向旧机 `E:\Ingulf\智能选型\网页端\_vendor\`。

这三个 skill 是远端最新提交（0b822de，11-18 前后）在旧机器上写的，换机后没做内容迁移。**one-click-migrate 搬得动数据，搬不动技能文本里的硬编码**——这是技能层的换机盲区。

修法（沿用 smart-selection 已验证的模式，约半天）：

1. 两个脚本的 `BACKEND_ROOT` 改为：环境变量 `SQ_HOME` 优先 → 其次按常见根（`D:/zhangkun/智能询价`、`~/智能询价` 等）探测 → 找不到就**中文报错并提示设置 `SQ_HOME`，绝不静默回退**。tool-selection 同理用 `SS_HOME`。
2. SKILL.md 里的命令改为引用环境变量/相对说明，不再出现任何盘符；把「pyc 只认 3.13、版本错静默返回空」这条保留（它是真坑）。
3. 顺手在 SKILL.md 标注本机实测状态（三菱 401 fail-closed 属上游问题，不是 skill 坏）。

### 3.2 挂载与仓库卫生缺口

- **豆包看不到这些技能**：本机 skill 扫描根含 `C:\Users\zhangkun\.agents\skills`，实测该目录下只有 `superpowers`，没有 my-skills junction。`scripts/link-skills.ps1` 默认挂 .workbuddy-ai / .claude / .codex 三处——**加一个目标根即可**（脚本本身支持 `-TargetRoot`）。
- **README 技能表缺 3 行**：远端新增 tool-selection / quotation-helper / mitsubishi-inventory 时没更新 README 表；本地未提交的那 1 行是 pdf-sample-extraction。合并后表里只有 4/7。
- **pdf-sample-extraction 整个目录未入库**（untracked）：它是完成度很高的技能（5 脚本 + 7 篇 references），却是全仓唯一没有 git 保护的技能副本——违反仓库自己「唯一物理来源」的定位。应 commit（push 按你的红线先问）。
- **git HTTPS 通道依赖本地代理**：全局 `http.proxy=127.0.0.1:10808`，代理没跑时 my-skills 的 HTTPS fetch 直接失败（本次改走 SSH 成功）。建议二选一：给 GitHub 配 `url."git@github.com:".insteadOf "https://github.com/"`，或把代理设为按环境启用。三个业务仓走 SSH 不受影响。

### 3.3 tool-selection 的能力覆盖落后项目两个身位

skill 只覆盖「替代查询」一件事，而 smart-selection 网页端现在有六大能力：跨品牌替代、**成套配刀**、**失效对策**、**标识释义**、**新品牌专查（22 品牌 35 万实体）**、**牌号适用矩阵**。技能描述里「选型」这个触发词会把配刀/失效类请求也吸进来，然后给不出答案。要么扩 skill，要么按下面 §4 拆成职责清晰的多个 skill（推荐后者，与 quotation-helper / mitsubishi-inventory 的边界写法一致）。

## 4. 新 skill 候选（按 ROI 排序）

### 4.1 `tooling-kit` — 成套配刀（P1，最高 ROI）

- **触发**：「配刀」「车削/铣削/钻削配一套」「M8 攻丝配底孔钻+丝锥」「直径 20 孔深 50 选钻头」。
- **入口已存在**：`web/selectkit.py` 有 `__main__` CLI（支持 `--dmin/--dmax/--depth`），13 工序、品牌可选、车/铣/钻闭环。薄包装即可，不需要写业务逻辑。
- **要沉淀的判断**（都在 CLAUDE.md 里）：双真源陷阱（云函数 LOGIC 模板 vs selectkit.py 是两份独立实现，skill 只走 web 侧并注明）；挤压丝锥底孔≠切削丝锥（查官方表，不用公称−0.5×螺距近似）；参数表直径 gap>25% 不套用；缺数据明确报缺不硬配。

- **工作量**：1 天内。

### 4.2 `failure-diagnosis` — 失效对策（P1）

- **触发**：「崩刃怎么办」「积屑瘤」「铣削振动」「刀片寿命短」。
- **入口已存在**：真源 `web/data/failure_countermeasures.csv`（2066 句，带 op 工序列），网页 `/api/failures?q=&op=`；小程序侧 `miniapp/data/failures.js` 离线同款。skill 直读真源 CSV 最稳（不依赖 Flask 是否在跑）。
- **要沉淀的判断**：14 类统一失效分类 + 多语言同义词归一；**按工序过滤必须带上「综合」**（跨工序通用对策，只按册过滤会丢行业通用知识——这是实测踩过的）；对策是样本原文句子，不替厂家发挥。
- **验收**：`崩刃+铣削` 返回 31 条/6 品牌且含综合册通用对策；纯 `崩刃` 46 条/10 品牌。
- **工作量**：半天。

### 4.3 `quote-document` — 报价单生成（P1，闭环最后一公里）

- **触发**：「给这 20 个型号出报价单」「导出 Word/PDF 报价单」「俄语报价单」「盖章」。
- **现状缺口**：quotation-helper 只到「型号 含税X」的复制文本；正式单据（docx/excel/pdf/png、5 语言、公司模板、印章、单号序列、有效期/付款方式）全部在 `backend/smart_quotation/export/` 里（quote_docx.py 48KB、i18n_terms.py、seal.py、document_sequences.py），但只有 admin GUI 一条路。**销售在聊天里问完价，下一步必然要单据——这是频率最高的未包装动作。**
- **入口**：走后端 `/api/export/*`（带 admin 鉴权，本地 SQ_DEV 或密钥），或直接调 export 模块。建议前者：列 schema/脱敏/审计/配额都在路由层，绕过去等于把不变量重抄一遍。
- **要沉淀的判断**（CLAUDE.md 导出节）：每行直传界面显示价、服务端不重算；列权威是 `copy.columns[].field`；company 角色列过滤+行白名单；≤5000 行；有效期/付款方式不填就不显示、绝不补默认天数；PDF/PNG 依赖 LibreOffice 且工作目录必须 ASCII 路径；公式注入前缀 `'`。
- **验收**：同一批型号，skill 出的 docx 与 GUI 出的逐字段一致（含单号递增、中文文件名 RFC 5987）；LibreOffice 缺失时 PDF 明确降级提示而不是报错。
- **工作量**：1–2 天（导出套件本身零改动，只做包装+鉴权配置）。

### 4.4 `price-import` — 价格表导入（P2）

- **触发**：「把这批价格表导进去」「列名对不上」「上传报告里告警是什么意思」。

- **要沉淀的判断**：数值清洗千分位/货币符/全角、清洗不出绝不静默归零；行主键优先级 stock_key>primary>searchable[0]>spec；库存行按 (code+货主) 保留；导入报告必须回答「数据去哪了」（dropped_rows/column_collisions）；别名分隔符集前后端同一份。

  - 假阳性纪律：漏抽类判据先用「已入库正确样本」反向对照（曾虚报近 800 条）；
  - 独立校验：验证器不复用抽取器规则（自证等于没验）；变异测试证明闸门真的会红；
  - ZK-AI：审查发现必须配回归测试、「还没做的别拿它当已修」。
- **形态**：一份 SKILL.md（流程+证据层级+输出格式）+ 交接提示词模板 + 「结论上提、过程下沉」的文档纪律。任何 harness 的任何 agent 拿到就能审。
- **工作量**：1 天（素材全是现成的，做的是提炼）。

## 6. MCP：`zk-tools` 业务工具服务器（P2，根因解法）

### 为什么是 MCP 而不是继续加 CLI skill

现在每个业务 skill 都是「一份脚本 + 一份 SKILL.md 文本」，路径、解释器版本、参数约定各抄一份——E:/Ingulf 事故证明这种形态天然漂移。而你的客户端已经不止一个：豆包、Claude Code、Codex、WorkBuddy、ZK-AI 任务台。**MCP 把「能力实现」收敛成一份，把「怎么触发」留给各客户端**：

```
QuotationEngine / substitute / selectkit / failures / grade 数据
        └── 一份 Python 包装层（路径走 paths.local.toml 模式）
              ├── CLI skill（现有形态，修好路径后继续用）
              └── zk-tools MCP server（HTTP，只读工具先行）
                    ├── ZK-AI 任务台 mcp_call（白名单机制已就绪）
                    ├── 豆包 / Claude / Codex 等任意 MCP 客户端
                    └── 服务器侧 agent（公网入口经 Caddy，需鉴权）
```

ZK-AI 侧**零新机制**：`cli_tools.yaml` 加一个 `backend: mcp` 执行体 + `mcp_tools` 白名单，`mcp_call.py` 的审批/任务空间围栏/参数校验直接复用。

### 工具清单（v1 全部只读）

| 工具 | 包装对象 | 备注 |
|---|---|---|
| `quote` | QuotationEngine.quote | 多租户 company_id 显式传参 |
| `substitute` | web/substitute.py | 3.13 解释器约束在服务器侧固化，客户端不再踩 |
| `selectkit` | web/selectkit.py | 13 工序 + 约束参数 |
| `failures` | failure_countermeasures.csv | op 过滤自动带「综合」 |
| `grade_lookup` | grade_group + gradematrix | 无冲突判据内置 |
| `stock` | mitsubishi_stock | **fail-closed 语义原样透传**，canary 失败返回结构化错误而非数字 |

写类（导入/发布/部署）**不进 v1**——它们有 GUI 审批与审计链路，MCP 化等于重做权限模型，违背「不绕审批」的既有决策。

### 节奏

P0 先把 CLI skill 路径修好并稳定运行两周 → 包装层接口定型 → 再 MCP 化（skill 与 MCP 共用同一包装层，**不允许出现第三份实现**）。部署与智能询价同机（它本来就依赖 quotation.db 与项目代码），公网暴露与否单独决策。

## 7. Agent 层：对齐「总控大脑」路线，不另起炉灶

ZK-AI `docs/总控大脑-能力矩阵与差距分析-20261105.md` 已把 agent 层缺口排成 R2–R6（cli_usage 账本 → 动态选执行体 → worktree 隔离 → 验收裁判 → 看板），且明确「不新建框架、不新建选模型层」。本报告完全沿用，只补三个与该路线正交的落点：

## 8. 跨项目优化点

### 8.1 智能询价的 LLM 列映射改走 ZK-AI 网关（P1，改一行配置）

`backend/smart_quotation/llm.py` 第 60 行已支持 `LLM_BASE_URL` 环境变量，但默认直连 NVIDIA NIM（kimi-k3，30 RPM 客户端限流）。你建网关就是为了「选模型/选 Key/失败转移」全包——**自己的业务绕自己的网关，等于网关的密钥轮换、兜底、用量统计对这条链全部失效**。改法：`.env` 设 `LLM_BASE_URL=http://127.0.0.1:8317/v1`（服务器侧走回环 8318）、`LLM_MODEL=zk-auto`（或长上下文别名）、`LLM_API_KEY=$ZKAI_API_TOKEN`，`LLM_RPM` 按网关侧限额重调。注意网关默认 max_tokens=1024，列映射响应短，够用；失败降级静态别名表的既有语义不变。

### 8.2 smart-selection CLAUDE.md 拆分（P2）

73,406 字节且每轮会话还在往里加，已超过 ZK-AI 用测试守门的 65,536 预算。两个兄弟项目都有现成解法：智能询价「规则手册 + docs/架构与关键链路 + 历史决策复盘」三层；ZK-AI「结论上提、过程下沉 + test_doc_scale 余量告警」。建议：把 §数据管线 里的会话性记录（重抽数字、备份路径、部署时间戳）迁到 `docs/管线纪要.md`，CLAUDE.md 只留铁律与指针；给仓库加同款字节预算检查。**规则写进文档≠会执行，预算守门要工具化**——这是 ZK-AI 已验证的教训。

### 8.3 skill-inventory 增加「可移植性 lint」（P0 的一部分）

现有盘点查引用状态/重复/废弃/位置，建议加三条扫描（都是本次实测抓到的问题家族）：

- SKILL.md 与 scripts 里的**绝对盘符路径 / 旧机器名**（`E:/Ingulf`、`D:\刀具文件` 这类）→ 标红；

- **挂载覆盖**：本机各 harness 的 skills 根是否都挂了 my-skills junction。

这是 one-click-migrate 的技能层对应物：换机后跑一次，死路径在造成误判前就被抓出来。

### 8.4 pdf-sample-extraction 回填新方法论（P2）

该技能铁律 15 自己要求「新踩的坑回填坑总表，技能是经验的唯一副本」，但 references 目前停在京瓷/泰珂洛时代。smart-selection 之后两轮沉淀的通用方法论还没进去：

- **锚点回归池**（374 条回原文验证过的断言，规则改动必跑；换源旧锚点退役）；
- **源指纹绑定**（每 PDF md5+页数，样本根变动先比指纹，防产物成孤儿）；
- **OCR 支线**（rapidocr 断点续跑；抽样验证必须按行自己的册键映射——曾闹出 0/30 假恐慌）；
- **batch2 通用管线**（品牌配置驱动 + 六类规则；牌号列头跨页重复率≥30% 自动排除；digit_band_ok 货号列判据；年份伪型号拦截）；
- **known-gaps 台账**（带原文证据/状态/日期，闸门只对未登记新增拦截，登记项不隐藏）。

这些都是「判断密集」部分，正是 skill 该承载的；脚本仍可留在项目里，skill 记判据与指针。

### 8.5 substitute 源码重建（P2，消除单点）

现状：`substitute.py` 是原生壳 exec 84KB pyc + `_patch_*.py` 补丁机制；`_pyc_recovered.py` 是**反汇编笔记**（含 `34| p = DATA ? name` 这类伪代码），不是可执行源码。整条替代查询业务仍压在一个只认 3.13 的字节码孤本上。重建条件其实已齐：行号表/字段名/docstring/字符串常量齐全 + `_baseline/` 10 项回归 + panel_sweep 0 不一致的验收口径。建议单独一轮：以笔记为底稿补全源码 → 回归逐字通过 → 壳退役。不做的话，至少把 pycbin 纳入 one-click-migrate 的必搬清单并在 skill 里保留丢失告警（现有写法已对）。
